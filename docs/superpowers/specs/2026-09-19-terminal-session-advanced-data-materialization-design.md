# 终态学生会话高级数据异步物化设计

**状态：** 设计已确认，本地实施完成，待审阅与发布
**日期：** 2026-09-19
**适用范围：** 课程高级数据、数据质量、研究会话物化与生产分析 worker

## 1. 问题与目标

当前高级数据和数据质量的部分读取路径会在 Web 请求中从原始会话、作答和行为事件重新构建完整研究数据包。学生集中作答时，教师刷新这些页面会与学生写入争抢 CPU，并可能使同步 Gunicorn worker 超时。

本设计将高级数据读取改为只读取预先生成的终态会话物化结果。学生作答与正式提交仍同步写入权威 PostgreSQL；只有分析投影异步生成。目标是：单个学生正常完成或由现有截止时间机制结算后，其数据在 60 秒内进入高级数据；仍在作答的学生完全不进入高级数据名单、统计或分母。

## 2. 已确认的产品语义

- 可见性的粒度是单个学生会话，不等待全班或整个实验结束。
- `completed` 会话可进入高级数据。
- 现有系统已经支持总时限、单题时限和任务截止，并由调度器结算到期会话；`expired` 会话也可进入高级数据。
- `in_progress` 会话不得出现在高级数据中。
- 沿用现有“已完成”“已超时”等状态，不新增另一套超时结算或终态枚举。
- 从会话形成终态到高级数据可见的目标上限为 60 秒。

## 3. 架构选择

复用现有 Django 单体、PostgreSQL、`analytics-worker`、`ResearchSessionMaterialization` 及其响应、访问和行为明细表。不新增 Redis、RabbitMQ、第二套 PostgreSQL、ClickHouse 或新的 Docker 服务。

Docker 容器只承担隔离计算职责，不作为独立业务真值存储。权威作答、提交、评分、截止时间、原始事件和审计事实继续保存在现有 PostgreSQL 业务表中；高级数据读取使用同库内的版本化物化表。

```text
学生写入/提交
  -> Django 事务同步保存权威数据
  -> 会话进入 completed 或 expired
  -> transaction.on_commit 轻量入队
  -> analytics-worker 单并发生成会话物化结果
  -> 完整结果原子发布为 current
  -> 高级数据与数据质量接口只读 current 物化结果
```

## 4. 写入与物化边界

学生端成功响应的前提保持不变：答案、正式提交、评分事实和终态事件必须在权威事务中完成。不得先向学生返回成功，再依赖异步任务补写正式答案或提交状态。

会话进入 `completed` 或 `expired` 后，事务提交回调创建物化任务。现有 30 秒调度循环负责扫描和补偿遗漏任务；`analytics-worker` 负责领取、续租、生成和发布。直接入队是正常路径，定时扫描只是恢复机制。

物化任务以学生会话为最小单元。一个任务失败不得阻塞其他会话。重复入队必须幂等，同一会话同一源版本不得并发生成多个有效结果。

## 5. 读取一致性与页面表现

- 高级数据和数据质量接口只能查询已成功且 `is_current=True` 的物化结果。
- 禁止在物化缺失、生成中或失败时回退到 `read_research_dataset()` 等实时全量构建路径。
- 终态会话在物化完成前不显示数据行；页面顶部只显示不含学生身份的汇总提示，例如“2 份数据正在生成”。
- 物化成功后，该学生的完整会话、响应、访问和行为数据一次性可见，不能暴露部分生成结果。
- 源数据发生合法修订时，旧 current 版本继续可读；新版本完整生成后再原子切换，避免读取半新半旧的数据。
- 页面显示数据生成时间、待生成数量、最老等待时长和失败数量。
- `completed` 与 `expired` 都进入物化结果，并沿用现有状态标签；`in_progress` 不进入列表、计数和分析分母。

## 6. 失败、恢复与资源隔离

物化 worker 保持单并发并设置明确的 CPU/内存边界，使学生作答 Web 服务优先获得两核主机资源。提高 Gunicorn 超时时间不是解决方案，因为它只会让低效计算更久地占用 worker。

任务使用现有租约、heartbeat 和有限重试机制。worker 停止或进程异常时不影响学生提交；恢复后继续处理队列。任务最终失败时记录失败状态和可诊断错误，教师页面仅显示失败数量，不把未发布数据当作可用数据，也不触发同步重算。

高级数据监控至少暴露：积压数、最老等待秒数、失败数和生成耗时 P95。若最老等待超过 60 秒，应触发运维告警，而不是让 Web 请求接管计算。

## 7. 现有实现差距

- 生产环境存在 `analytics-worker`，但高级数据物化功能开关尚未启用。
- 高级数据主接口已有物化读取分支，可作为统一读取路径。
- 数据质量接口仍直接调用 `read_research_dataset()` 构建完整数据集；该路径已在生产产生超过 60 秒的 worker timeout，必须改为读取物化结果。
- 启用配置前必须检查所有高级数据入口，确保没有其他接口绕过物化层。
- 历史终态会话需要有界、分批、错峰回填；不得在学生集中作答期间一次性全量生成。

## 8. 发布策略

第一阶段只对课程 2 使用现有课程白名单开启，保留全局关闭开关。先完成历史终态会话的限速回填，再验证新产生的 `completed` 和 `expired` 会话。验证通过后才扩大课程范围。

配置启用、代码发布和历史回填是三个独立步骤。任何一步失败都应能通过关闭物化读取开关停止扩大影响，但关闭后不得自动恢复到高成本实时重算；页面应明确显示高级数据暂不可用或仍在生成。

## 9. 验收标准

1. `in_progress` 学生不出现在高级数据名单、统计或分母中。
2. `completed` 和 `expired` 会话在终态形成后 60 秒内可见，并显示现有状态标签。
3. 连续刷新高级数据或数据质量页面不会重新构建完整研究数据包，也不会重复创建有效物化任务。
4. 学生集中作答期间同时刷新教师数据页面，不产生 Gunicorn worker timeout 或该路径的 500。
5. 已物化的高级数据读取目标低于 2 秒，且不会随全部原始事件总量呈明显线性退化。
6. 停止 `analytics-worker` 不影响学生答题、保存和提交；恢复后积压任务继续处理。
7. 重新物化期间旧完整版本持续可读，新版本成功后原子切换。
8. 单个任务失败不阻塞其他会话，并可从监控中看到失败与积压。
9. 历史回填期间 Web 健康检查、学生提交成功率和延迟不出现明显恶化。
10. 针对正常完成、总时限结算、任务截止结算、活动会话、重复入队、worker 崩溃恢复及物化失败建立自动化回归证据。

## 10. 非目标

- 不异步化权威答案、正式提交、评分或截止时间判定。
- 不改变学生作答、计时、草稿、提交、幂等、writer lease、事件采集或断网恢复语义。
- 不新增终态、超时结算规则或教师可见的学生身份信息。
- 不建设微服务、消息中间件、独立分析数据库或新的 Docker 存储区。
- 不以增加服务器内存、提高超时或增加同步 Web worker 代替消除实时全量计算。
